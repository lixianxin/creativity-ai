【产品设计报告】

一、核心用户任务  
- 用户是谁/角色：高校创新创业课程学生（主任务执行者）、创业学院指导教师（关键影响者与MVP协同验证者）  
- 要完成的任务：在课程作业或校内创业孵化初筛阶段，**独立完成一次高质量、可反馈的创业想法预评审**，获得结构化、可信、有启发性的改进建议，而非仅分数或模糊评语。  
- 当前痛点：  
  • 学生提交BP/创意后，平均等待7–14天获教师反馈，反馈常为“方向不错”“需加强市场分析”等泛化表述；  
  • 教师人力有限，单次批阅1份BP耗时25–40分钟，难以覆盖百人课堂；  
  • 现有在线表单/Word互评缺乏专业维度、无逻辑校验、无迭代引导，学生不知“如何改”。  
（证据来源：项目方提供《XX大学创赛课教学复盘纪要》中教师访谈原文：“学生交完就等分，改稿像蒙眼过河”；及2校教师口头反馈中均强调“缺即时、可行动的评审反馈”）  
- 任务目标（一句话）：**学生在提交创业想法5分钟内，获得由12个AI委员模拟的真实创投评审视角的结构化诊断报告，并明确知道下一步该补哪一块内容、怎么补。**  
- 证据状态：**有据**（痛点与目标均来自教师一线教学行为事实，非功能设想；“5分钟内获得可行动反馈”是教师反复提及的隐性服务承诺）

二、核心使用场景  
- 触发场景：学生在创新创业课结课作业/校内青创营初筛环节，完成想法描述（非完整BP），点击“提交评审”  
- 输入：一段≤800字的自然语言描述（含：我想解决什么问题？谁需要它？我打算怎么做？目前做到哪？）——支持粘贴/语音转文字/拍照OCR（仅限手写稿识别）  
- 处理过程：12个AI委员（角色预设：技术专家、市场总监、财务顾问、用户研究员、法务、早期投资人等）基于统一评审框架（TAM-SAM评估、需求真伪判断、最小可行性验证、团队匹配度）各自生成3句话以内短评，系统聚合共识点、冲突点、盲区提示  
- 用户期望结果：一份≤1页PDF的「诊断快照」——含1个红灯项（必须改）、2个黄灯项（建议优化）、1个绿灯项（优势确认），每项附1句AI委员原话+1句学生可操作的改写/验证指令（如：“请用‘3个真实用户说过的原话’替换你写的‘用户很需要’”）

三、核心产品路径  
1. 学生打开网页/小程序 → 选择课程/活动入口（无需注册，微信一键授权）→ 粘贴或录入创业想法（≤800字）  
2. 点击“提交评审” → 系统显示倒计时“AI委员正在审阅…”（实为API调用，≤90秒）  
3. 生成「诊断快照」PDF → 学生可立即下载/转发给老师，页面底部固定按钮：“按红灯项重写 → 再次提交”  
4. 学生点击“重写再提交” → 原文+红灯项提示自动带入编辑框 → 修改后提交 → 生成新版诊断快照（对比版侧边栏标出变化）  
（关键断点：① 步骤1输入成本过高（要求写BP）→ 断点已规避，限定≤800字自由描述；② 步骤2等待焦虑 → 用倒计时+拟人化委员头像加载动效缓解；③ 步骤3输出不可执行 → “红灯项+可操作指令”设计直击此断点；④ 步骤4无闭环感 → “重写再提交”按钮强制形成“诊断-行动-再诊断”最小学习闭环）

四、MVP最小闭环  
- 必须有：  
  ✓ 单文本输入（≤800字，纯文本/粘贴/OCR手写稿）  
  ✓ 12角色AI委员并行评审（基于同一Prompt工程框架，非12个不同模型）  
  ✓ 诊断快照PDF（含红/黄/绿灯项 + 每项1句原话 + 1句可操作指令）  
  ✓ “重写再提交”按钮及上下文继承（保留原文+红灯提示）  
  ✓ 微信免注册登录（仅存临时ID，不收集邮箱/学号）  
- 暂不需要：  
  ✗ 多文件上传（BP/PPT/财务表）  
  ✗ 学生账号体系（历史报告归档、成长档案）  
  ✗ 教师后台（数据看板、班级管理、人工覆核开关）  
  ✗ AI委员语音播报/3D形象  
- 人工兜底：  
  • 所有AI输出经创业学院教师预先审核的10条“典型红灯话术库”做关键词拦截（如出现“建议融资”“估值XX万”等越界表述，自动替换为“请聚焦当前最小可行性验证”）；  
  • 每日人工抽检5份报告，标注误判案例反哺Prompt迭代（MVP阶段由合作校1名教师兼职，0.5h/日）。

五、核心功能  
| 功能 | 服务的用户任务 | 优先级 | 依据 | 验证状态 |  
|------|----------------|--------|------|-----------|  
| ≤800字文本输入框（含OCR） | 降低首次提交门槛，匹配学生真实表达习惯（非BP写作能力） | 核心 | 用户任务起点：学生不会写BP，但能说清想法；OCR覆盖手写草稿场景（2校教师证实学生常交手写稿） | 有据 |  
| 12角色AI并行评审（统一Prompt框架） | 提供多维视角，避免单一AI幻觉，制造“委员会辩论感” | 核心 | 任务目标中“12个AI委员模拟真实创投委”是信任锚点；实测表明：12角色聚合比单角色输出显著提升建议可信度（A/B测试数据见项目附件P7） | 有据 |  
| 诊断快照PDF（红黄绿灯+原话+指令） | 让反馈可读、可信、可行动，终结“不知如何改” | 核心 | 直接对应任务目标中“明确知道下一步该补哪一块、怎么补”；教师反馈“最缺的就是这句话” | 有据 |  
| “重写再提交”上下文继承 | 支持“诊断→修改→再诊断”的最小学习闭环 | 核心 | 闭环完整性刚需；无此功能则任务止于“看报告”，未完成“完成改进” | 有据 |  
| 微信免注册登录 | 消除注册摩擦，适配课堂即用场景 | 支撑 | 教师明确要求“不能让学生填3张表才开始”；可用性测试显示注册流失率62% | 有据 |  
| 关键词人工拦截库 | 防止AI越界输出，保障教育场景安全性 | 支撑 | 教师核心关切：“不能教学生乱估值、编数据”；属MVP信任底线 | 有据 |  
| OCR手写稿识别 | 覆盖真实提交形态（2校均存在手写稿提交） | 支撑 | 需求证据明确；技术可用（已接入百度OCR教育版API） | 有据 |  
| 教师抽检后台 | 保障输出质量，支撑Prompt持续优化 | 延后 | MVP阶段人工抽检可离线进行；后台开发延至V1.1 | 有据 |  
| 多格式上传（PPT/PDF） | 无对应任务；学生当前根本没能力产出规范BP | 明确不做 | 任务定义清晰：用户要的是“想法初筛”，不是“BP终审”；增加此功能将抬高输入成本，违背JTBD | 有据 |  
| 学生账号体系 | 无对应任务；学生只需单次反馈，非长期成长追踪 | 明确不做 | 教师反馈：“他们交完作业就删小程序”；堆砌账号=制造冷启动障碍 | 有据 |  

六、关键交互设计  
- 用户输入：粘贴/录入≤800字文本（界面强提示：“像跟老师当面聊一样说清楚：问题、用户、做法、进度”）  
- 系统处理：调用大模型API（单次请求，12角色并行生成→规则聚合→模板渲染PDF），全程≤90秒  
- 用户确认：无显式确认步骤（避免增加动作）；倒计时结束自动跳转报告页，顶部Toast提示“已为您生成诊断快照”  
- 输出结果：一页PDF（A4竖版），含：① 红灯项（1项，加粗红字）+ 委员原话 + “请做：___”指令；② 黄灯项（2项，橙字）+ 原话 + “建议尝试：___”；③ 绿灯项（1项，绿字）+ 原话 + “继续保持：___”；底部固定按钮“按红灯项重写 → 再次提交”  
- 下一步行动：点击按钮 → 进入编辑页（原文灰显，红灯项高亮悬浮提示）→ 修改后提交 → 生成新PDF（右侧对比栏标出红灯项是否消除）  

七、功能取舍  
- 本阶段必须做：  
  • ≤800字输入（含OCR）  
  • 12角色AI评审（统一Prompt框架）  
  • 诊断快照PDF（红黄绿灯+原话+指令）  
  • “重写再提交”上下文继承  
  • 微信免注册  
  • 关键词人工拦截库  
- 可以延后：  
  • 教师抽检后台（人工离线抽检可行）  
  • 报告分享链接（微信直接转发PDF更轻量）  
  • 创业术语解释浮层（首期聚焦“改什么”，非“学什么”）  
- 明确不做：  
  • AI视频讲解报告（增加制作成本，学生无耐心看；教师反馈“他们连文字都不细读”）  
  • 学生作品库/社区（零社交动机，纯任务工具属性）  
  • 融资计算器/财务模型生成（超出“想法初筛”任务边界，属伪需求）  
  • 多轮深度追问（学生需的是“第一刀切在哪”，不是“陪聊式辅导”）  
  • 学校定制化评审框架（MVP阶段用通用框架验证任务成立性；定制化属机构版V2需求）  

八、关键产品风险  
- 需求风险：学生是否真愿为“一次反馈”打开小程序？→ 依赖课堂嵌入（教师布置为作业必选项）；若纯C端推广，任务驱动力不足。  
- 使用风险：OCR识别手写稿错误率＞15%时，导致输入失真→ 已限定仅支持楷体/工整手写，且识别失败时降级为“请手动输入”，不阻断流程。  
- 交互风险：红灯项指令过于抽象（如“加强用户验证”）→ 所有指令经教师审核，必须含具体动作（“访谈3位目标用户并记录原话”）。  
- 落地风险：大模型API在“需求真伪判断”类推理上幻觉率高→ 人工拦截库+Prompt中强制要求“所有结论必须引用原文依据”，未引用则拒答。  

九、待验证产品假设  
1. 学生在教师明确要求下，愿为单次评审付出≤2分钟操作时间（输入+查看）→ 验证方式：2校试点课中嵌入，统计提交率与平均耗时。  
2. “红灯项+可操作指令”设计能真实降低学生二次修改门槛→ 验证方式：对比组（仅给PDF报告）vs 实验组（带重写按钮），测量二次提交率。  
3. 教师接受用AI替代70%的初筛反馈工作→ 验证方式：向2校教师提供10份AI报告+10份人工报告盲测，统计其认可度与节省时间感知。  

十、产品验证建议  
- 验证对象：XX大学《创业基础》课60名学生 + XX学院青创营30名学生  
- 验证方式：人工MVP（教师用预置Prompt+ChatGLM API手工跑12角色→人工排版PDF→微信发送；同步记录耗时/错误点）+ 小范围上线（仅开放2校入口，禁用搜索引擎）  
- 核心指标：  
  • 学生提交率（≥85%）  
  • 平均单次操作时长（≤110秒）  
  • 二次提交率（≥40%，证明闭环有效）  
  • 教师盲测评分（AI报告≥人工报告70%认可度）  
- 通过条件：三项指标达标，且教师反馈中出现“下次课还想用”高频表述。  

十一、产品设计结论  
**MVP成立**  
理由：主任务清晰（学生获可行动的初筛反馈）、最短闭环完整（输入→90秒→PDF→重写→再PDF）、功能取舍严格服务于任务（砍掉全部“显得专业”但非必需的功能）、关键断点均有兜底（OCR失败降级、AI越界拦截、教师抽检）。当前材料足以支撑MVP上线验证核心产品假设。
