# 产品设计官案例1：二手书-最小交易闭环

- 平台：deepseek / deepseek-v4-flash
- 耗时：135.3s，tokens：1892+13545

## 输入

项目名称：校园二手书交易平台
项目描述：我要做一个校园二手书交易平台，目标用户是全国大学生，平台从每笔订单抽取5%服务费，我预计第一年做到10万用户。我觉得平台需要：物流系统、智能推荐、社区论坛、信用评价、在线支付、晒单分享、会员体系、新人优惠券。
目标用户：全国大学生
核心痛点：未提供
解决方案：校园二手书交易撮合平台
商业模式：每笔订单抽5%服务费
当前阶段：想法阶段

## 产品设计输出

【产品设计报告】

一、核心用户任务

- 用户是谁/角色：项目方表述为“全国大学生”。这不能直接作为 MVP 用户定义；更为重要的是，买方与卖方是两个不同角色、两个不同任务，不能笼统混成“一个用户”。MVP 必须先选定一侧或先选定一个具体校园场景再验证。
- 要完成的任务：项目材料没有提供核心痛点，也没有提供用户任务证据。“我要做校园二手书交易平台”是一个解决方案描述，不是“学生要完成什么任务”的任务描述。
- 当前痛点：未提供。不可替项目方编造。
- 任务目标：目前无法可靠定义为一句话。若硬写只能写成“某校某专业学生在学期内买到/卖掉一本指定教材”，但这仍是假设。
- 证据状态：信息不足。

二、核心使用场景

以下整段为 **假设，待验证**，不是已经确认的产品场景。

- 触发场景：学期初选课结束后，学生发现课程要求购买指定教材，但新书价格高、学长手里有旧书却找不到；或学期结束/毕业季，学生需要处理旧教材。
- 输入：课程名、书名/ISBN/版次、书况、期望价格、所在校区、可交易时间。
- 处理过程：买方查找或提交需求，卖方发布或等待匹配，双方确认版本与价格后约定交易方式。
- 用户期望结果：以比买新书更低的价格、比四处打听更短的时间，买到/卖出一本指定教材。

三、核心产品路径

以下整段为 **假设，待验证**，基于“买方先找指定教材”的路径示意。

1. 学生输入课程名称/书名/ISBN，或直接发布求购需求。
2. 系统/运营返回匹配书目，展示价格、书况、所在校区、卖方联系方式。
3. 买方确认购买或联系卖方，核对版本、书况、价格。
4. 双方面交或快递，完成付款，买方确认收到。

关键断点：
- 第 1 步最大断点是“没有书源”——如果卖方不发布，买方搜索为空。
- 第 2 步最大断点是“版本/书况不透明”，学生不敢买错版次。
- 第 4 步最大断点是“交付/信任成本太高”，导致用户觉得不如直接在班级群里喊一句。
- 另有一个平台级断点：学生可能在第 2 步之后直接加微信线下交易，平台被绕过，5% 服务费无法成立。

四、MVP最小闭环

当前信息不足以定义“最终产品必须有”。但如果进入需求验证阶段，**本阶段最小闭环可以不是系统，而是人工MVP**：

必须有：
- 一个有真实课程与教材需求的具体校园试点，例如某一所大学的一个年级或学院；
- 一个足够简单的信息登记工具，如微信群+腾讯文档/表单；
- 一个负责匹配、核对版本与提醒交易的人工运营者；
- 一个可执行的交付与付款方式，建议先用线下见面交付+当面转账。

暂不需要：
- App/小程序开发；
- 物流系统、在线支付、信用评价体系、智能推荐；
- 社区论坛、晒单分享、会员体系、新人优惠券。

人工兜底：
- 书源不足时，由运营手动在自己的同学群、二手群、毕业群寻找书源；
- 版本和书况不确定时，由运营要求卖方上传封面/版权页照片；
- 出现履约问题时，由运营介入协调。

五、核心功能

由于主任务未验证，以下功能表是“假设主任务成立后的初步分级”，不等同于已验证需求。

| 功能 | 服务的用户任务 | 优先级 | 依据 | 验证状态 |
|---|---|---|---|---|
| 二手书供给/需求信息发布与浏览 | 买方知道哪里有书、卖方知道谁要书 | 核心 | 项目方定义“撮合平台”，无此功能无法撮合 | 假设待验证 |
| 教材ISBN/版本/书况结构化展示与确认 | 避免买错版本或书况不符 | 核心 | 教材与普通书不同，版本与课程强相关 | 假设待验证 |
| 交易与支付 | 完成订单资金流转 | 支撑，可延后 | 校园场景可先用线下转账+人工确认替代 | 假设待验证 |
| 信用评价 | 降低陌生交易的不信任 | 支撑，可延后 | 真实校园身份、线下见面、人工兜底可部分替代 | 假设待验证 |
| 物流系统 | 服务于跨校/异地履约 | 不做 | 项目方未提供交易是同校还是跨校的证据；同校面交场景用不到 | 不做（场景未验证） |
| 智能推荐 | 帮用户发现想买的书 | 不做 | 教材需求通常是明确ISBN/课程，搜索比推荐更短；“逛书”需求无证据 | 不做 |
| 社区论坛 | 让用户交流讨论 | 不做 | 不服务于“买到/卖出一本教材”的主任务；只会造成表面活跃 | 不做 |
| 晒单分享 | 传播与口碑 | 不做 | 增长手段，不是 MVP 必要功能；先验证主任务再谈传播 | 不做 |
| 会员体系 | 增加用户留存与复购 | 不做 | 二手书交易季节性极强，复购逻辑未验证；不影响单笔任务完成 | 不做 |
| 新人优惠券 | 刺激首单转化 | 不做 | 需求未被验证前，补贴会掩盖真实痛点 | 不做 |

六、关键交互设计

以下整段为 **假设，待验证**，以“买方先提交求购需求”为示意。

- 用户输入：一句话或表单填写“课程名/书名/ISBN+期望价格+书况要求”。
- 系统处理：匹配已有供给；若暂无书源，则保留需求，等待之后新发布的卖方匹配。
- 用户确认：买方确认具体某一本书的版本、价格、书况。
- 输出结果：给出可预约的线下交易地点/时间，或直接给出卖方联系方式。
- 下一步行动：买方联系卖方、完成取书和付款。

注意：学生成交路径越短越好。现实中“在微信群里发一句：谁有《XX》教材？”可能比填写复杂表单更快。因此产品设计上应尽量降低输入成本，例如支持拍照封面自动识别ISBN，甚至由人工运营辅助补全信息。

七、功能取舍

本阶段必须做：
- 只在一个具体校园场景内验证“学生找指定教材并成交”这一件事；
- 用最轻量方式解决书源发现、版本确认、交易履约；
- 先人工，再谈自动化。

可以延后：
- 在线支付：MVP 可用线下转账，后续等需求验证后再考虑；
- 信用评价：MVP 可用真实校园身份+线下见面+人工兜底替代；
- 物流系统：若未来验证存在稳定的跨校交易场景，再考虑。

明确不做：
- 智能推荐：不服务“学生找到特定教材”这一个确定任务；
- 社区论坛：没有证据表明“社区活跃”会带来二手书交易；
- 晒单分享：只作用于增长，不作用于验证核心任务；
- 会员体系：在交易尚未成立时做会员是典型的功能堆砌；
- 新人优惠券：未验证自然需求前做补贴，会掩盖“用户是否真的需要这个产品”的判断。

八、关键产品风险

- 需求风险：用户痛点未提供。“二手书交易”可能并不是真问题，或者已经被班级群、校内二手群、跳蚤市场、学长转赠等低门槛渠道解决了。
- 使用风险：教材版本、书况、卖家是否真实、交付地点与时间是否匹配，任何一个环节失败交易都会中断。
- 交互风险：如果为了“平台全面”加入社区、会员、优惠券等，会让完成交易的最短路径变长；学生可能选择绕过平台直接联系。
- 落地风险：直接面向“全国大学生”做平台会遭遇供给密度不足、教材版本差异大、物流成本高、季节性集中、双边冷启动这几个问题。MVP 必须落到“一个学校一个年级一个教材周期”，否则连撮合都难以发生。

九、待验证产品假设

1. 需求假设：大学生确实存在“指定教材不好低价获取”或“闲置教材不好处理”的痛点。
2. 渠道假设：这个痛点没有被校内群、二手群、图书馆、电子书、复印店等现有渠道低成本解决。
3. 付费假设：学生愿意在成交后让平台抽取 5% 服务费，而不是在知道卖方联系方式后线下跳单。
4. 供给密度假设：在同一个学校/学院/年级内，指定教材的版本重复度足以形成真实交易；如果同一门课不同老师用不同版本，会是致命问题。
5. 线上化增量假设：如果只用微信群+表格就能撮合成交，学生仍然愿意迁移到一个独立产品上完成交易，说明产品有增量价值。

十、产品验证建议

- 验证对象：一个具体大学中最容易形成相同教材需求的学院或年级，例如基础课程统一、必修课集中的专业。
- 验证方式：不开发系统。在开学季建立“XX大学教材求购群”，用腾讯文档/表单收集“课程名+书名+ISBN+期望价格”，运营人工作为中介去现有二手群、毕业群找书源，促成线下交易。记录学生是否会绕过运营直接私下成交。
- 核心指标：
  1. 在一个教材周期内提交真实求购需求的人数；
  2. 能成功匹配到具体书源的比例；
  3. 真实成交订单数；
  4. 从发出需求到成交的平均时长；
  5. 在没有补贴的情况下，是否有下个学期继续使用的行为信号。
- 通过条件：至少在单校区、单一教材周期内出现一批真实成交，并且买卖双方不是因为人情、补贴或运营强行搓合才完成交易；用户下一步仍愿意回同一个渠道找书/卖书。达不到这个条件，不应进入系统开发。

十一、产品设计结论

信息不足，无法可靠判断。

原因是：项目方没有提供核心用户痛点和真实的触发场景；“全国大学生”不是 MVP 可服务的产品边界；项目方所列物流系统、智能推荐、社区论坛、信用评价、在线支付、晒单分享、会员体系、新人优惠券不能在没有主任务的情况下被定义为“需要做的功能”。

如果要进入下一轮产品判断，请项目方补齐最小信息：
1. 准备先在哪个学校/学院/年级验证？
2. 买方和卖方分别是谁？先启动哪一侧？
3. 学生目前用什么方式买/卖二手教材？卡在哪一步？
4. 教材版本是否统一？同校交易还是跨校交易？
5. 5% 服务费由买方出还是卖方出？在没有验证前，这只是一个商业模式假设，不是产品需求。

在补齐这些信息之前，我给出的产品建议是：先做人工 MVP，不开发系统，不等同于“项目不能做”。
