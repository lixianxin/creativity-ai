三、核心产品路径
- 说明：因“主任务”未定义，核心路径无法被推导。以下为假设示意，全部标注为“假设，待验证”。
- 假设（待验证）：假设用户为初高中生，场景为日常作业/课后复习时遇到难题，求助于AI学习助手。
1. 触发：学生写作业/复习时，遇到不会的题/不确定的知识点。（断点：题目输入方式是否低成本？拍照比打字更低成本，但拍照后识别精度直接决定用户是否继续。）
2. 用户动作：打开应用，对准题目拍照，或输入题目文字。（输入成本：拍照的清晰度和镜头对准偏差。断点：如果第一张照片OCR识别失败/识别错误，没有纠错引导，用户会退出。）
3. 系统处理：识别题目 → 返回“答案解析 + 相似知识点讲解”或“知识点讲解”（核心）。
4. 用户确认：看答案/讲解是否看得懂。若仅给答案，用户抄完之后任务即终止，但学习闭环尚未达成；（断点：用户拿到答案后直接离开，产品无法验证“掌握”，也无法沉淀留存素材，即学习数据）。
5. 用户期望结果：能独立理解这类题目的解法，下次遇到能自己做对。
6. 断点：获取了讲解后，怎么证明掌握？如果不做自主验证（如再做一题），用户学完即走，产品难产生二次打开价值。

四、MVP最小闭环
- 必须有：
  - 单一任务入口：以“拍照搜题/解题”为唯一任务核心（前提是项目方确认“求助解题”是最核心高频需求）。
  - 拍照/文字OCR识别→ 题库/知识库检索 → 返回答案/解析 → 对“没看懂”的二次讲解入口。
- 暂不需要：
  - AI错题本、智能学习计划、AI聊天陪伴、学习社区、积分商城、排行榜——若以“解题”为最小闭环主题，这些全部是“延后”功能，不服务本次核心任务。
- 人工兜底：
  - MVP阶段题库覆盖率有限，对未检索到的题目，必须有“人工答疑/求助入口”或“告诉用户该题暂无法解析”的信息，并用人工方式回应用户，保证用户获得了可执行结果，否则断点无法闭环。

六、关键交互设计
- 用户输入：拍照（自动/手动框选区域）→ 确认题目已拍全 → 点击“找解答”。
- 系统处理：OCR识别 → 返回“题目解析/知识点”，用分步方式呈现，避免只给最终答案。
- 用户确认：此处需增加“我是否已理解”的判断，让用户点击“明白了/没明白，再讲一遍”，以此确保输出结果是可执行的掌握，而非抄写。
- 输出结果：题目详解 + 对应知识点讲解，并推荐一道同类型题让用户试做（只提示“再做一题”，服务“掌握验证”）。
- 下一步行动：用户试做返回是否掌握；已掌握则完成闭环，未掌握则重复讲解或转人工答疑。
- 关键断点：若从题目直接跳到“知识点讲解”，对基础薄弱学生不可行；解释中需要针对错选/错因进行解释，避免用户看完“觉得懂了”，实则未掌握。

七、功能取舍
- 本阶段必须做：“解题 + 答案讲解 + 同类题验证”（前提是项目方选定“解题求助”为MVP主任务，且用最小用户样本验证）。
- 可以延后：AI错题本、智能学习计划——需先积累用户解题行为/错误记录，才有“错题”和“计划”的输入；无输入则功能形同虚设。
- 明确不做：（项目方提出但不服务主任务的功能）
  - AI聊天陪伴：属“情感陪伴”任务，不是“学习辅助”任务；只会增加内容审核风险，且无法解释它如何服务“解题/掌握”。
  - 学习社区：缺少“讨论对象”和“内容源”，社区运营成本高；初期做社区等于做另一个产品。
  - 积分商城、排行榜：属于用户激励体系。在没有一个已验证的核心学习任务闭环前空建激励体系，会误导产品重心到“玩游戏”而非“做学习”。
  - “第一版必须全做”：这是“功能全集”思维，不服务任何真实用户任务。本阶段必须砍掉该方案，否则产品在定义阶段即失败。

八、关键产品风险
- 需求风险：目标用户“所有学生”过于宽泛，不同学段/学科诉求完全相反。未选任何一种用户场景，任何开放做都是伪需求风险。
- 使用风险：拍照搜题路径极高依赖题库覆盖与 OCR 识别准确度。若经常“找不到题”或“识别错”，即使用户下载也会立即卸载。
- 交互风险：若“讲解”只是答案堆砌，用户会抄完就关闭应用，“掌握”目标无法达成，产品无价值沉淀。
- 落地风险：广告盈利模式依赖日活跃用户数和高频使用率，而“搜题”通常是偶发高频、过程低频场景，广告收益能否覆盖成本严重存疑（但此问题交由财务与商业模式官判定）。

九、待验证产品假设
（以下假设因项目方当前信息中无任何证据，全部要验证后才会成立）
1. 需求假设：学生用户当前的“最大学习痛点”是“遇到难题时得不到及时的答案和讲解”，而非“缺少学习计划/错题管理/陪伴”等。
2. 使用假设：用户对“基于拍照解题的一次性任务”能产生周/月高频使用（足够支撑广告），而非只在考试前打开一次。
3. 供给假设：题库和知识库覆盖率能支撑“核心题目的解析”，且讲解质量比用户内部群/搜题软件中现有解法有明显更好体验。
4. 差异假设（待竞品官提供数据）：“现有的同类搜题工具/搜索引擎”解答不了当前“所有学生”的难题，因此用户需要再装一个新App。

十、产品验证建议
- 验证对象：选定一个单一目标群体（例如：初三/高一学生）+ 单一学习场景（每天作业/刷题场景）。
- 验证方式：人工MVP/假门测试。
  - 不用先做App。拉20~50名目标学生入微信群，让学生直接丢题目/作业截图，项目方/运营人工（或调用GPT+人工复核）快速返回“答案+知识点讲解”，用3天体验完最短路径。
  - 另一组可做“假门测试”：做一个最简H5，只包含“拍照解题+结果页/讲解+再来一题”，广告试验放在“完成一次任务后”的位置，看是否有人持续使用、能否有留存。
- 核心指标：请求量（日均每人提问）、首问解答成功率、讲解后用户是否回到群/H5再来一题、3日后留存率、广告可展示次数/用户人均行使任务次数。
- 通过条件：所选目标用户中在为期3天的体验中，每天主动发起任务≥1次；首问解决后的“再做一题”完成≥50%；可见广告曝光至少达到单用户日均2次；若指标不达标，不能进入下一个版本。

十一、产品设计结论
产品假设存疑。当前项目方期望交付的是一个“八合一产品大全”，没有给出目标更精确的使用场景、用户任务或痛点证据，方案本身建立在“功能全就有竞争力”的假设之上。在目前证据状态下，无法可靠设计出能被点出的核心产品闭环，也无法支持“第一年100万用户”的直接判断。项目应先选择并验证一个“高频单学习任务”（例如基于解题求助的答案+讲解闭环），验证后再决定是否扩展为错题本/社区/积分等功能。
