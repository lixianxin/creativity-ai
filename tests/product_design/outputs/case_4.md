# 产品设计官案例4：自习室-查找预约短路径

- 平台：deepseek / deepseek-v4-flash
- 耗时：118.5s，tokens：1919+11343

## 输入

项目名称：本校考研自习室预约小程序
项目描述：我只做本校考研学生的自习室预约，学校周边有3家自习室，目前空位靠微信群登记、经常抢不到。已访谈120名备考学生，68人表示愿意每月付300元买固定座位。用户的核心需求是快速知道哪里有空座位并能锁定座位：查找可预约座位→预约→到店使用。我打算先做微信小程序。
目标用户：本校考研学生
核心痛点：空位靠微信群登记、经常抢不到
解决方案：微信小程序预约
商业模式：向自习室抽佣10%
当前阶段：想法阶段（有120人访谈，未上线）

## 产品设计输出

【产品设计报告】

一、核心用户任务
- 用户是谁/角色：本校考研学生，备考期间需要稳定、可控的自习座位。
- 要完成的任务：快速知道周边 3 家自习室哪里还有空座，并能够真正锁定一个座位，到店后直接使用，避免在微信群里手速抢座、抢到后还可能不被确认的问题。
- 当前痛点：空位信息依赖微信群人工登记，不实时、不透明、无法锁定，热门时段经常抢不到。
- 任务目标（一句话）：本校考研学生在需要自习时，打开小程序即可看到周边合作自习室的可预约空座，完成预约锁定，并按预约到店学习。
- 证据状态：需求假设待验证。项目方访谈了 120 名备考学生，68 人愿意每月付 300 元买固定座位，这验证了“愿意为稳定座位付费”；但产品当前定义的“查找空座→预约→到店使用”是临时性预约场景，与“购买固定座位”不完全等同。核心任务存在“临时抢约空座”与“长期固定座位”两种可能，需先补证再开发。

二、核心使用场景
- 触发场景：考研学生当天或第二天需要到自习室学习，尤其是晚间、考前等高峰时段，已知微信群抢座成功率低，于是打开小程序查看哪里还有空座。
- 输入：日期/时间段、偏好的自习室位置；首次使用需要微信授权手机号。
- 处理过程：小程序读取 3 家自习室的可预约座位库存；学生看到每家自习室的空座情况；选择某个可约座位；确认预约；系统锁定该座位并生成凭证。
- 用户期望结果：预约成功，得到一个明确的座位和到店凭证；到店后不需要再被微信群或前台口头安排，能够直接入座。

三、核心产品路径
1. 学生打开小程序，授权手机号，进入“自习室空座”首页。
   - 关键断点：授权流失。微信一键授权成本可接受，但要避免强制填写学号、上传学生证等额外步骤。
2. 学生选择自习室和日期/时间段，查看可预约座位列表。
   - 关键断点：空座数据由谁更新、是否实时。若数据靠前台人工发布，可能出现显示有座但实际无座；预约锁定必须能反向校验。
3. 学生点击“可约”座位，确认预约。
   - 关键断点：多人同时抢同一座位。必须做到“预约即锁定、锁定时即时占用”，否则只是把微信群登记搬进小程序，没有解决核心痛点。
4. 系统生成预约成功凭证，同步推送至学生端和自习室管理端。
   - 关键断点：若自习室前台看不到预约单，就无法承认预约结果；初期必须有人工接收/核销闭环。
5. 学生到店出示凭证，前台核销并安排入座。
   - 关键断点：座位爽约、超卖、自习室不认线上凭证等问题。可用人工核销兜底，但要提前与自习室约定规则。

四、MVP最小闭环
- 必须有：
  - 3 家自习室的基础信息与座位/时段库存（初期可由后台人工维护）
  - 学生端“可约座位查询”
  - 座位/时段的预约与锁定
  - 预约成功凭证（预约号或二维码）
  - 取消预约并释放座位
  - 自习室前台可查看“已预约名单”并核销的简易后台
- 暂不需要：
  - 小程序内线上支付（可到店付款，或线下周期结算；否则会增加支付资质、退款、分账复杂度）
  - 固定座位/月卡购买
  - 实时座位传感器、硬件改造
  - 校方认证、学生证上传
  - 地图导航、智能推荐、消息模板提醒等增强体验功能
- 人工兜底：
  - 座位库存更新由自习室前台定时维护或预约后自动锁定+前台人工确认；初期允许“以锁代查”。
  - 到店核销由前台人工完成。
  - 出现座位冲突、超卖、爽约时，由项目方或前台人工协调改约、退款或现场换座。

五、核心功能

| 功能 | 服务的用户任务 | 优先级 | 依据 | 验证状态 |
|---|---|---|---|---|
| 自习室列表与空座查询 | 让用户快速知道哪里有空座 | 核心 | 直接对应用户“空位靠微信群、经常抢不到”的痛点 | 痛点明确，但真实使用频次与时段待试点验证 |
| 座位/时段预约并锁定 | 让用户真正锁定座位，避免手速抢不到 | 核心 | 预约锁定是解决“微信群登记不确定性”的关键动作 | 有访谈支撑用户愿意为稳定座位付费，但“预约锁定”本身待验证 |
| 预约凭证生成与展示 | 让用户到店可以使用，完成“预约→到店”闭环 | 核心 | 没有凭证，到店就回到人工确认状态 | 基本需求成立，待场景验证 |
| 取消预约与释放座位 | 防止约错后占座浪费，保证可预约库存真实 | 支撑 | 预约类任务的自然延伸；没有取消机制会造成恶意占座和空位浪费 | 需求假设待验证 |
| 自习室端订单查看与核销 | 前台能确认预约并完成线下交付 | 支撑 | 线下交付需要同步信息，否则线上预约无法落地 | 需通过自习室合作试点验证 |
| 线上支付/分账 | 支撑商业模式落地 | 延后 | 商业模式为抽佣 10%，但产品核心任务完成不依赖小程序内支付 | 无直接证据；可到店付款或线下结算替代 |
| 固定座位/月卡购买 | 满足“每月 300 元买固定座位”的潜在真实任务 | 延后 | 访谈证据指向该需求，但与当前“临时预约空座”的主任务不同 | 有访谈证据，但未验证产品形态与供给端协作 |
| AI 推荐、学习数据分析、社区、考研内容等功能 | 不服务当前主任务 | 不做 | 功能堆砌会把核心路径拖复杂，增加开发与运营成本 | 无需求来源 |

六、关键交互设计
- 用户输入：选择自习室 → 选择日期/时间段 → 点选一个“可约”座位 → 点击“确认预约”。
- 系统处理：后台根据当前库存和已预约记录，将选中座位状态改为“已预约”，生成唯一预约凭证；同时通知自习室前台端新增一条待核销订单。
- 用户确认：提交前显示确认页：自习室名称、地址、时段、座位号、到店时间；确认后显示“预约成功”和凭证信息。
- 输出结果：预约成功页包含预约码/凭证文字、自习室地址、前台电话，以及“取消预约”入口。
- 下一步行动：学生到店出示凭证；前台核销；若预约后不能到店，学生可提前在小程序内取消，系统释放座位。
- 关键交互断点：当用户所选时间段无空座时，系统应立即展示附近其他自习室或相邻时段的可用座位，避免用户因“查不到座”直接离开。

七、功能取舍
- 本阶段必须做：
  - 空座查询、座位预约与锁定、凭证生成、取消预约、前台核销后台。
- 可以延后：
  - 线上支付、固定座位月卡、消息订阅提醒、学生身份认证、座位偏好收藏、消费记录与订单统计。
- 明确不做：
  - 固定座位长期租赁：当前 MVP 尚未确认主任务是“临时预约”还是“固定月卡”，如果直接做，会要求完全不同的库存模型，先不做。
  - 自习室评价系统、研学社交、拼座、研友匹配：不服务于“快速锁定自习座位”这一主任务。
  - 考研资料、课程推荐、商城：一旦引入，平台角色会从工具变成内容平台，超出当前阶段。
  - AI 座位预测、智能推荐：没有数据基础，且当前 3 家自习室的库存完全可以通过预约锁定解决，不需要“预测”。
  - 多校区/多城市扩张：先把本校周边 3 家跑通。

八、关键产品风险
- 需求风险：访谈验证的是“愿意每月 300 元买固定座位”，而不是“每次通过小程序预约并支付服务费”。如果用户真正要的是“固定座位”，那么当前“临时预约”产品可能是伪需求；如果用户要的是“高峰期临时抢座”，则平台不增加座位总量，抢不到问题未必真正缓解。
- 使用风险：微信群登记对用户几乎没有学习成本；小程序若每次还要打开、选座、确认、抢锁，比微信群复杂，用户可能只在“抢不到时才想起用”，导致留存低。
- 交互风险：空座状态不实时会造成“线上有座、到店没座”的信任崩塌。核心不是做展示，而是做锁定：只要被预约，状态必须立即变为已约。
- 落地风险：3 家自习室为什么愿意接入？10% 抽佣对自习室可能缺乏吸引力；若空位本身供不应求，自习室不需要引流，配合动力低。同时，自习室若不承认线上预约凭证，整个闭环不成立。

九、待验证产品假设
1. 主任务假设：用户需要的是“临时预约空座”，而不是“一次性购买固定座位/月卡”。需先验证哪种任务更高频、更刚性、更愿意付费。
2. 付费假设：学生愿意为“预约成功/锁定座位”支付额外费用；或自习室愿意为获客承担 10% 佣金。访谈中的 300 元/月不能直接证明平台抽佣模式成立。
3. 供给假设：3 家自习室愿意配合提供库存并承认线上预约锁定；即使空位信息由前台人工更新，也能保持基本准确。
4. 行为假设：学生在晚高峰、考前抢座时，会放弃微信群，改用小程序完成预约并到店核销；而不是只在小程序里“看两眼”又回微信群报名。

十、产品验证建议
- 验证对象：核心任务是“临时预约空座”还是“固定座位月卡”；用户是否愿意为了“预约锁定”付出额外成本；3 家自习室能否接受线上订单核销。
- 验证方式：人工 MVP / 假门测试，不先做完整小程序。
  - 与 3 家自习室各约定一定数量可预约座位，要求“线上预约成功后必须为平台用户留座”。
  - 用共享表格或极简页面展示“自习室—时段—剩余座位”。
  - 邀请访谈中愿意付费的目标学生进入试点群，通过表单提交“我要预约某自习室某时段座位”。
  - 运营人员人工锁座、回复预约成功凭证。
  - 学生到店时报凭证，前台人工核销。试点期间不要求线上支付，到店或线下结算。
  - 同时测试另一组“每月 300 元固定座位”的购买意愿与成交率，用于判断主任务方向。
- 核心指标：
  - 试点期间提交预约的人数与每人预约次数
  - 预约成功后的到店核销率
  - 因信息不准、超卖导致的冲突次数
  - 学生相比微信群继续使用小程序的意愿
  - 自习室对“线上预约留座、10% 抽佣”的接受度
  - 学生对“固定座位月卡”与“临时预约空座”二选一时的选择比例
- 通过条件：
  - 连续 2 周内，有至少 30 名真实考研学生完成预约并到店核销；
  - 到店核销率不低于 80%，未出现系统性超卖冲突；
  - 至少 2 家自习室愿意继续参与试点并接受线上核销模式；
  - 能清晰看出用户更偏向“每日预约”还是“固定月卡”，以此决定正式 MVP 的产品形态。

十一、产品设计结论
MVP 部分成立，待补证。

理由：用户、场景、痛点基本清晰，最短闭环可以定义为“查空座→预约锁定→到店核销”，功能取舍也能做到克制；但访谈证据指向“固定座位月租”这个可能更强的需求，与当前“临时预约空座”的产品定义存在冲突。必须先补证“用户要的到底是稳定座位，还是临时抢座预约”，否则产品可能做出来一个“比微信群更快的登记工具”，却并没有满足用户真正想要的“稳定获得自习座位”。建议先做人工试点验证主任务方向，再投入微信小程序完整开发。
