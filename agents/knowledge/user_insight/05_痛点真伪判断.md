# 痛点真伪判断

用户洞察官必须判断项目方声称的痛点是真痛点还是伪需求。核心方法是看**用户现在怎么解决**。

## 真痛点的特征

1. **高频发生**：用户经常遇到，不是一年一次。
2. **用户已有解决行为**：用户在用某种方式解决（哪怕很笨），说明真的在意。
3. **用户为解决付出过成本**：时间、金钱或精力。
4. **现有方案不满意**：用户对现有方案有明确抱怨。

## 伪需求的特征

1. **低频**：用户很少遇到，遇到了也不觉得是大问题。
2. **用户没有解决行为**：嘴上说需要，但从来没试图解决过。
3. **用户没付过任何成本**：没花过钱、没花过时间找替代方案。
4. **现有方案其实够用**：用户对现状没有强烈不满。

## 判断方法：追问"现在怎么解决"

对项目方声称的每个痛点，必须追问：
- 用户现在怎么解决这个问题？
- 用户为这个解决方案付了多少钱/时间？
- 用户对现有方案哪里不满意？
- 如果没有解决方案，用户会怎样？

如果用户现在没有任何解决行为，大概率是伪需求。

## 高频刚需 vs 低频伪需求

| 维度 | 高频刚需 | 低频伪需求 |
|------|----------|------------|
| 发生频率 | 每周/每天 | 每月/每年 |
| 现有方案 | 有但不满意 | 没有或无所谓 |
| 付费意愿 | 已为解决付费 | 未付过费 |
| 切换动力 | 强 | 弱 |

## 结论输出

- 真痛点且有付费行为：需求成立。
- 真痛点但无付费行为：部分成立待补证。
- 伪需求：不成立。
- 无法判断用户现有解决行为：证据不足。
